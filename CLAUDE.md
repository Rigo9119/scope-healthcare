## Architecture

This is a **React SPA** (TanStack Router) backed by **Sanity CMS**, deployed on Netlify. The repo has two independent packages:

- `/` — Frontend (Vite + React 19 + TanStack Router + Tailwind CSS v4)
- `/studio` — Sanity Studio v3 (separate `package.json`, separate `node_modules`)

### Data flow

Content is fetched at runtime from Sanity (project `3fyb50d2`, dataset `production`) via `src/lib/sanity.ts`. Every page component loads Sanity data and falls back to the inline `FALLBACK` constant if the fetch fails or returns null. GROQ queries live in `src/lib/queries.ts`.

### Routing

File-based routing via TanStack Router. Add route files under `src/routes/`. **Never edit `src/routeTree.gen.ts`** — it is auto-generated by `tsr generate` (runs via vite plugin on dev, or manually with `generate-routes`).

**Locale-prefixed URLs:** the active locale lives in the path (`/es`, `/en`).
- `routes/index.tsx` (`/`) only redirects to `/{locale}` (remembered Paraglide locale, else `es`).
- `routes/$lang/route.tsx` is the locale layout — its `beforeLoad` validates `lang ∈ {es,en}` (else redirects to `/es`) and calls Paraglide `setLocale(lang)` before render.
- **Real pages go under `routes/$lang/`** (e.g. `routes/$lang/index.tsx` is the home page). New routes are added there, not at the root.

### i18n (two-layer)

**UI strings** (nav labels, static copy): Paraglide JS via inlang.
- Source files: `messages/es.json` (base) and `messages/en.json`
- Generated output: `src/paraglide/` — **do not edit these files**
- Usage: `import { m } from '#/paraglide/messages.js'` → `m.key_name()`
- Base locale is `es`. Add new keys to both JSON files.

**Page content** (hero, specialties, testimonials, etc.): Sanity document-internationalization plugin.
- Documents follow the ID convention `homePage-{locale}` (e.g. `homePage-es`, `homePage-en`)
- The `useLang()` hook (from `src/i18n.tsx`) exposes `locale` (derived from the URL path — see Routing) and `switchLocale` (navigates to the other locale's path); pass `locale` to `fetchHomePage(locale)` to load the correct Sanity document

### Sanity Studio structure

Schemas live in `studio/schemaTypes/` split by type:
- `documents/` — top-level document types:
  - `homePage` — page content (hero, stats, specialties, process, why-us, testimonials, CTA)
  - `siteSettings` — global footer + contact, a per-locale singleton ("Configuración del sitio")
- `objects/` — reusable embedded types (`hero`, `statItem`, `specialtyItem`, etc.)

Studio uses a custom structure (`studio/structure/index.ts`) that surfaces one editor per locale for each document ("Página de inicio" and "Configuración del sitio") instead of a generic document list. Both are registered with the document-internationalization plugin and use `{type}-{locale}` IDs (e.g. `homePage-es`, `siteSettings-en`).

### Design system

All design tokens are defined in `src/styles.css` inside `@theme {}` (Tailwind v4 convention). Key decisions:
- **Primary color**: navy blue, `--color-primary-500: #1059b5`
- **Headings**: `font-heading` → Poppins; **Body**: `font-body` → Open Sans
- **Shape language**: sharp corners (no border-radius) throughout UI
- **Semantic tokens**: use `text-text-primary`, `bg-bg-page`, `border-border-default`, etc. rather than raw neutrals
- **Button shadows**: named shadow tokens (`shadow-btn-primary`, `shadow-btn-white`, etc.)
- `.link-animated` utility class in `src/styles.css` for underline-on-hover nav links

### Icon mapping

Sanity stores icons as string names; they're resolved to Lucide components in `src/components/Icon.tsx` via `ICON_MAP` and the `<IconComponent name="..." />` wrapper. When adding a new icon reference in Sanity content, import the icon and add an entry to `ICON_MAP`.

### Layout & components

The home page is composed from components under `src/components/`: `ui/` (BrandMark, Eyebrow, Stars, ImagePlaceholder), `layout/` (Navbar incl. TopBar, Footer), and `sections/` (Hero, StatsBand, Specialties, CareJourney, WhyUs, Testimonials, CtaBand). Section props are typed via `Pick<HomePageData, …>`.

**Navbar and Footer are global chrome rendered once in `src/routes/__root.tsx`** — inside `LangProvider` and `SiteSettingsProvider`, not per page. New routes render only their own content into the `<Outlet />`. Footer/contact data comes from the shared `useSiteSettings()` context (a single `fetchSiteSettings(locale)` shared by the TopBar and Footer); home-page content comes from `fetchHomePage(locale)`. Fallbacks live in `src/lib/homeFallback.ts` and `src/lib/siteSettingsFallback.ts`.

### Path alias

`#/` resolves to `./src/` in both Vite and Vitest configs.

## Deployment

The frontend and the Studio are **two independent deploys** — they ship separately.

### Frontend (Netlify)

`netlify.toml` builds the root SPA only: `npm run build` → publishes `dist/`, with an SPA catch-all redirect (`/*` → `/index.html`, 200). The `/studio` package is **not** built or served by Netlify, so the Studio is **not** reachable at `<site>/studio` by default.

### Sanity Studio (Sanity hosting)

Deployed to Sanity's free hosting, independent of Netlify:

```bash
cd studio && bun --bun run deploy
```

First run prompts for a hostname → Studio goes live at `https://<hostname>.sanity.studio`. Re-run after any schema/structure change. The project `3fyb50d2` is owned by `rigo4791@gmail.com`; the CLI login (`sanity login`) uses that same account — no new account needed.

### Client handoff

The deployed Studio URL loads for anyone, but **editing requires project membership**. Invite the client at <https://manage.sanity.io> → project **Scope Health** (`3fyb50d2`) → **Members** → **Invite** (set role to **Editor** for content-only access). They then log in at the `*.sanity.studio` URL.

> To instead serve the Studio under the main domain at `<site>/studio`, you'd build it into the Netlify output with `basePath: '/studio'` in `studio/sanity.config.ts`, add a `/studio/*` redirect **before** the SPA catch-all in `netlify.toml`, and register the Netlify origin via `sanity cors add`. This couples the two builds, so the standalone `*.sanity.studio` deploy above is preferred for handoff.

## Development practices

### Mobile-first
Write styles mobile-first: base classes target small screens, then layer `sm:`, `md:`, `lg:` overrides. Never write desktop styles first and try to undo them at small breakpoints.

### Language
All copy defaults to **Spanish**. Write Spanish labels, CTAs, section headings, and nav from the start. English is only needed for `messages/en.json` (i18n mirror) or foreign-patient testimonials.

### Content before routes
Lock in design tokens and refine existing pages before adding new routes. Don't scaffold new routes until the current page's design is approved.

### Aesthetic — clinical, not SaaS
The brand is a medical tourism clinic: light, bright, calm, trustworthy. Avoid dark navy full-bleed backgrounds, neon glows, glassmorphism (`bg-white/5`), grid/dot backdrops, and SaaS product widgets. Prefer white + `primary-50` surfaces, soft shadows, real medical content (specialties grid, care-journey steps, trust signals, contact bar).

### Hero sections
Avoid large empty dead space. Use split 2-column layouts (text left, visual/social-proof right) or fill the viewport with enough content. A centered single-column hero with `min-h-screen` and little content will leave ~60% dead space.

### Gradients
For gradient-heavy elements, use inline `style={{ background: 'linear-gradient(...)' }}` with explicit hex values instead of Tailwind gradient utilities at the 800–950 range (they render near-black).

## Linting & formatting

Biome (not ESLint/Prettier) for the frontend. Config in `biome.json`:
- Indent: **tabs**
- Quotes: **double**
- `src/routeTree.gen.ts` and `src/styles.css` are excluded from Biome

The Studio uses its own ESLint + Prettier config (single quotes, no semis).
